# Lab 01: The Event Loop Is the Game Loop (Biplane Game)

Мультиплеєрна браузерна гра про повітряні бої на біпланах (Клієнтська частина, Етап 1).

## Результати експериментів (M4)

### Експеримент 1: Блокуючий цикл у кадрі (Busy-wait)
* **Що робилося:** Додано синхронне затримання `while (performance.now() < t + 100)` під час рендеру кожного 60-го кадру.
* **Показники HUD:** `frames/s` різко впав з 120 до ~35-40 FPS, а `frame ms` зростав до >100 ms.
* **Пояснення через Event Loop:** JavaScript виконується в єдиному головному потоці (Call Stack) за принципом run-to-completion. Синхронний цикл повністю заблокував потік, через що Event Loop не міг передати керування на фазу малювання (Paint Step) браузера.

### Експеримент 2: `setInterval` замість `requestAnimationFrame`
* **Що робилося:** Ігровий цикл було переведено з `rAF` на `setInterval(frame, 16)`.
* **Показники:** З'явилося мікросмикання кадру (jitter), `frame ms` постійно коливався. При згортанні вкладки браузер зменшив частоту спрацьовування таймера до 1 Гц, що призвело до накопичення викликів та ривка при поверненні.
* **Пояснення:** `rAF` викликається суворо перед фазою малювання та паузиться у фоні. `setInterval` розміщує колбеки в Task Queue без прив'язки до розгортки монітора.

### Експеримент 3: Змінний крок (Variable Timestep)
* **Що робилося:** Прибрано акумулятор, симуляція викликалася один раз за кадр із реальним `dt`. Увімкнено 6x CPU Throttling у DevTools.
* **Показники:** За 5 секунд затиснутої тяги біплан при різному навантаженні CPU опинявся у зовсім різних точках арени.
* **Пояснення:** Змінний `dt` робить фізику недетермінованою через похибки інтегрування при низькому FPS. Фіксований крок (60 Hz) гарантує однакову траєкторію на будь-якому залізі.


## Lab 02 — Об’єкти, прототипи та `this`: модель сутностей

### Реалізована архітектура
- **`Vector2` (`src/sim/vector.js`)**: імутабельні (чисті) векторні операції (`add`, `sub`, `scale`, `normalize`, `rotate`, `dot`, `static fromAngle`) + in-place методи для гарячих ділянок.
- **`Entity` (`src/sim/entity.js`) та `Ship extends Entity` (`src/sim/ship.js`)**: один рівень успадкування. Унікальний `#id` генерується через приватне статичне поле `static #nextId`. Здоров'я корабля інкапсульоване в приватному полі `#hp` з публічним геттером `get hp()`.
- **`World` (`src/sim/world.js`)**: менеджер сутностей поверх `Map<id, Entity>` з ітератором `[Symbol.iterator]()`, генератором `*ofKind(kind)` та відкладеним видаленням (`despawn` → `Set` → `sweep()` наприкінці кроку).
- **Система колізій (`src/sim/collision.js`)**: відокремлена функція `detectCollisions(world)` коло–коло, яку в наступних лабах можна замінити на spatial hash без зміни ігрового циклу.

### Баг із `this` у `ship.fire` та варіанти виправлення

**Проблема:** Якщо передати метод безпосередньо як колбек у слухач подій:
```js
canvas.addEventListener('pointerdown', world.ship.fire);
у момент кліку браузер викликає функцію без контексту об'єкта ship (або з this = canvas для DOM-подій). В ES-модулях діє strict mode, тому при голому виклику спрацьовує Default binding (this === undefined), і спроба прочитати this.canFire() або this.pos викликає TypeError: Cannot read properties of undefined.

Обраний фікс (стрілкова функція-обгортка):

JavaScript
onFire: () => {
  const bullet = world.ship.fire();
  if (bullet) world.spawn(bullet);
}
Плюси: не створює зайвих замикань на кожному екземплярі класу, дозволяє одразу передати створену кулю у world.spawn(bullet).

Мінуси: потребує обгортки в місці підписки на подію.

Альтернативи та їх компроміси:

ship.fire.bind(ship) (Explicit binding): назавжди прив'язує this до конкретного екземпляра ship. Мінус: створює нову функцію-обгортку при виклику bind, а якщо корабель перестворять новим об'єктом, старий слухач залишиться прив'язаним до старого екземпляра.

Поле класу зі стрілкою fire = () => { ... }: стрілка захоплює this лексично в конструкторі. Мінус: замість одного спільного методу на Ship.prototype створюється окрема функція в пам'яті для кожного екземпляра.
Композиція замість глибокої ієрархії класів (Design Write-up)
Як виглядала б ієрархія при успадкуванні:
Якби ми будували гру через класи для кожної комбінації властивостей, дерево розрослося б уже на 4–5 рівнів:

Plaintext
Entity
 └── MovingEntity
      ├── Ship
      │    └── ShieldedShip / RapidFireShip
      ├── Bullet
      │    └── HomingBullet
      └── Asteroid
           └── HomingAsteroid
Коли нам знадобилося, щоб і куля (Bullet), і міна-астероїд (Asteroid) мали самонаведення, а бонус (Pickup) був нерухомим об'єктом із колізією без логіки корабля, жорстка ієрархія зламалася б: довелося б або дублювати код повороту до цілі в HomingBullet і HomingAsteroid, або вводити множинне успадкування, якого в JS немає.

Чому обрано композицію (src/sim/components.js):

Усі сутності наслідують Entity рівно на 1 рівень (Ship, Bullet, Asteroid, Pickup, Explosion).

Поведінка самонаведення винесена в незалежний компонент createHomingComponent(...) та чисту функцію applyHomingBehavior(entity, dt, world). Будь-яка сутність отримує самонаведення просто через поле this.homing = ....

Бонуси (Pickup) описують свою поведінку як дані (effect: { type: 'shield' | 'rapidFire' | 'homing', duration }) замість створення окремих підкласів ShieldPickup, RapidFirePickup тощо. Це робить сутності гнучкими та простими для серіалізації по мережі в наступних лабах.
